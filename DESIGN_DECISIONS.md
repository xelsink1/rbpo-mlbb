# Проектные решения безопасности WiseDubs

## Граница и статус

WiseDubs — локальное HTTP API для безвозмездной передачи вещей и бронирования общих комнат. Назначение и полномочия определены в [паспорте](PROJECT.md), обязательные свойства — в [SR](SECURITY_REQUIREMENTS.md), сценарии нарушения и единственный архитектурный вид — в [модели угроз](THREAT_MODEL.md). Здесь зафиксированы инженерные решения S04 для будущей реализации на ASP.NET Core, PostgreSQL и Docker Compose.

Решения приняты для проектирования. На S05 создана техническая основа: API, PostgreSQL и `GET /health`; её инструкция и фактические проверки находятся в [паспорте](PROJECT.md#10-локальный-запуск). Регистрация, сеансы и предметные механизмы D пока не реализованы. Все таблицы будущих проверок ниже — планы, а не выполненные испытания. Для фактического результата нужны версия и интерпретация. Данные вымышленные, ОС и Docker доверенные, запросы пользователей недоверенные. Подтверждение email, внешний доступ и прикладные интеграции исключены.

Шесть D выделены по самостоятельным механизмам: допуск, выдача данных, состояние вещи, бронирование, обработка ввода/эксплуатационная граница и учёт попыток. Число записей не является показателем качества. Весь приоритетный набор T-01, T-03–T-08, T-11, T-12 связан с решениями и проверками; остальные угрозы также учитываются. ID связанного SR ведёт к его критериям приёмки, таблица проверки уточняет условия механизма.

<a id="d-01"></a>
## D-01. Аккаунт, сеанс и актуальные полномочия

**Контекст.** Обоим сценариям нужен установленный сервером пользователь. Уникальность логина нельзя обеспечивать только предварительным чтением, а семидневное подтверждение с неизменяемой ролью не обеспечивает выход и отзыв административных прав.

**Решение.** API использует одну нормализацию email: удаление крайних пробелов и приведение к нижнему регистру через `ToLowerInvariant()`; нормализованное значение хранится под ограничением уникальности PostgreSQL. Регистрация выполняет только вставку обычного пользователя, без обновления при конфликте и без принятия роли из запроса. Конфликт, включая конкурентный, даёт отказ без изменения прежнего аккаунта; при сбое вставка откатывается. Вход использует ту же нормализацию.

Пароль хеширует и проверяет стандартный `PasswordHasher<TUser>` с `IdentityV3`: PBKDF2-HMAC-SHA512, случайная соль 128 бит, результат 256 бит, явно заданные 220 000 итераций. Самостоятельный криптографический алгоритм не создаётся. Стоимость проверки предстоит измерить на целевом компьютере. Основа выбора — [реализация Microsoft](https://source.dot.net/Microsoft.Extensions.Identity.Core/PasswordHasher.cs.html) и [ориентир OWASP для PBKDF2](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2); соответствие всему стандарту или FIPS не заявляется.

При успешном входе криптографический генератор создаёт 32 случайных байта, представляемые как Base64url. Клиент получает подтверждение один раз в ответе входа и передаёт `Authorization: Bearer …`. В PostgreSQL сохраняются уникальный SHA-256-хеш подтверждения, ID пользователя, время выдачи, окончание через 7 × 24 часа и признак прекращения. Хеш случайного подтверждения не используется для паролей. Только после фиксации записи сеанса API возвращает успех; неизвестное или повреждённое значение не даёт пользователя.

В целевом продукте защищённые операции закрыты по умолчанию; без входа доступны регистрация и вход, а также техническое исключение `GET /health`. Исключение выполняет только `SELECT 1`, выдаёт фиксированный статус готовности без предметных данных и не устанавливает пользователя или права. В основе S05 реализован только этот технический маршрут. Для каждого будущего защищённого запроса сервер читает сеанс и актуальную роль пользователя из БД, проверяет отсутствие прекращения и `текущее время < окончание`. Пользователь и роль из тела запроса не определяют права. Затем проверяется конкретный объект: автор объявления, получатель текущего резерва либо владелец брони. У администратора дополнительных прав на чужие договорённости нет; состояние и время изменений уточняют D-03/D-04. Недоступность проверки не разрешает операцию. Долговременного кеша сеансов и ролей нет.

Выход атомарно прекращает текущую запись сеанса. Успешный ответ следует после фиксации; последующие запросы с сохранённым подтверждением отклоняются. Оператор выдаёт/отзывает роль через служебное подключение средствами доверенного окружения по ID аккаунта. Это не маршрут API: после фиксации отзыва следующий административный запрос читает новую роль, даже с прежним сеансом.

**Доверенные данные.** Сохранённый аккаунт, запись сеанса и роль после служебного изменения; время сервера. Контактный email и присланные идентификаторы сами по себе не доказывают полномочия.

**Обоснование и альтернатива.** Непрозрачное подтверждение с серверной записью подходит для одного локального API: срок, выход и роль проверяются в одном источнике. Применимая альтернатива — подписанный JWT с серверным реестром отзыва и отдельным чтением актуальной роли. Он сохраняет нужные свойства, но добавляет подпись, ключи и два основания проверки, не устраняя обращения к БД. JWT только со сроком и ролью внутри не является эквивалентом. Пересмотр уместен при нескольких сервисах с обоснованной потребностью автономной проверки; тогда немедленный отзыв надо обеспечить отдельно.

**Связи:** T-01, T-02, T-03, T-04, T-05, T-11 → [SR-01](SECURITY_REQUIREMENTS.md#sr-01-допуск-после-входа-и-сохранность-аккаунта), [SR-02](SECURITY_REQUIREMENTS.md#sr-02-ограниченный-жизненный-цикл-сеанса), [SR-03](SECURITY_REQUIREMENTS.md#sr-03-полномочия-и-принадлежность-объектов), [SR-08](SECURITY_REQUIREMENTS.md#sr-08-защита-учётных-данных-и-секретов). Нераскрытие секретов дополнительно обеспечивает D-05.

**Будущие проверки:**

| ID | Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- | --- |
| P1 | Действующий пользователь A; гость | Прямое чтение и изменение без Bearer, с изменённым/случайным Bearer; затем правильный вход | Отказы не раскрывают предметные данные и не меняют их; вход даёт отдельную запись сеанса и разрешённое действие по SR-01/02. |
| P2 | Один ранее свободный email | Одновременно зарегистрировать варианты регистра/крайних пробелов с разными паролями; повторить регистрацию занятого логина | Ровно одна вставка, второй запрос не перезаписывает данные; прежний пароль и сеансы сохраняются. В хранилище — хеш с выбранными параметрами, без исходного пароля. |
| P3 | Два сеанса A; управляемое серверное время | Выполнить частые обращения до границы срока; выйти из первого, повторить Bearer; проверить второй непосредственно до и на границе 7 дней | Сроки не продлеваются; первый прекращён, второй действует до своего срока и отклоняется на границе. |
| P4 | Объекты A; пользователь B, в том числе с ролью администратора | Подставить ID A, автора/владельца и роль в запросах | Отказ либо создание только от текущего пользователя по SR-03; чужие записи не меняются. |
| P5 | Администратор с действующим сеансом | Оператор фиксирует отзыв роли; затем выполняется новый административный запрос с прежним Bearer | Изменение справочника отклоняется; обычные действия над собственными объектами остаются доступны. |

**Ограничения.** Украденное действующее подтверждение даёт доступ до прекращения/срока; владелец компьютера, ОС и Docker входят в доверенное окружение. Уже допущенный запрос не отзывается задним числом. Перезапуск API не должен сбрасывать срок или отзыв, поскольку источник в БД. Новые сервисы или кеширование требуют пересмотра проверки сеанса и актуальных полномочий.

<a id="d-02"></a>
## D-02. Выдача только разрешённых представлений

**Контекст.** Вход не разрешает чтение всей записи. Получатель вещи виден автору только во время текущего резерва, а расписание не раскрывает владельца и цель брони. Ограничение только общей ленты оставляет обход по ID или через ответ изменения.

**Решение.** API формирует явные DTO с разрешённым набором полей, не сериализует сущности БД и вложенные профили целиком. Списки, карточки, запросы по ID и ответы изменений используют одни правила выбора данных. Публичные в пределах входа представления отделены от собственных объектов пользователя.

- Опубликованное объявление содержит контакт автора, место и состояние. Email входа не добавляется автоматически. Третьим пользователям доступен факт занятости без ID резерва и получателя, его имени или контакта.
- У автора сведения получателя добавляются только при наличии текущего активного резерва; у получателя — только о собственном текущем резерве. Запрос старого ID не возвращает прежние связи. После прекращения резерва новое чтение использует уже зафиксированное состояние. Снятое объявление выдаётся только автору.
- Занятость содержит комнату и интервал. Отдельное чтение собственных броней фильтруется по установленному пользователю и включает цель, состояние и сохранённые сведения о комнате. Чужая запись по ID не выдаёт частное представление даже администратору.

Поля видимости и соответствующие связи читаются согласованно в одном запросе к БД; для ответа изменения используется состояние этой операции. Межпользовательского кеша предметных ответов нет. Обработчик отказа не помещает закрытую запись в текст ошибки.

**Доверенные данные.** Пользователь из D-01, принадлежность и текущее сохранённое состояние объекта. Решение о полях принимает API, а не интерфейс клиента.

**Обоснование и альтернатива.** Разрешённый набор исключает случайное добавление нового поля сущности в ответ. Альтернатива — сериализация сущности с условными исключениями полей — применима, но требует контролировать каждую новую связь и каждую ветвь сериализации. Явные представления проще проверить для разных читателей; при новых полях правила DTO и проверки пересматриваются вместе.

**Связи:** T-06 → [SR-04](SECURITY_REQUIREMENTS.md#sr-04-ограничение-раскрытия-данных); текущее состояние резерва и история обеспечиваются D-03/D-04.

**Будущие проверки:**

| ID | Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- | --- |
| P1 | Автор A, получатель B, третий C и администратор; действующий резерв | Каждый прямо читает списки, карточку, резерв по ID и ответы изменений | Поля различаются строго по SR-04; C и администратор не получают сведения B или вложенный профиль, email входа не появляется автоматически. |
| P2 | A сохранил ID резерва B | Зафиксировать отмену или снятие, затем повторить чтение по старым ID; создать новый резерв | Старые имя, ID и контакт не выдаются; при новом резерве автор видит только текущего получателя. Снятое объявление получает только A. |
| P3 | Будущие, текущие, прошедшие и отменённые брони A; удалённая из справочника комната | A, B и администратор читают расписание и историю, подставляют чужой ID | В расписании только неотменённые интервалы без владельца/цели; полная собственная история сохраняется у A, посторонним недоступна. |

**Ограничения.** Уже полученные сведения нельзя отозвать у клиента. Чтение, сформированное до прекращения связи, не является новым чтением после него. Сохранение истории до сброса не означает её доступность другим пользователям; будущий кеш или новый интерфейс требуют повторной проверки всех путей выдачи.

<a id="d-03"></a>
## D-03. Атомарное состояние вещи и идентичность резерва

**Контекст.** Несколько получателей, снятие автором и отмена могут одновременно менять одно предложение. Кроме конкуренции существует повтор команды, относящейся к уже прекращённому резерву.

**Решение.** Текущее состояние, ID резерва, ID получателя и контакт получателя хранятся в строке объявления. Для состояния «зарезервировано» текущие поля обязательны; для «свободно» и «снято» они отсутствуют. Это согласованность полей, закрепляемая ограничением БД, без независимого флага активного резерва. Каждое резервирование создаёт новый UUID резерва, не переиспользующий прежние ID.

Все операции над существующим объявлением выполняются в транзакции `READ COMMITTED`: `SELECT … FOR UPDATE` по ID объявления, повторная проверка принадлежности/состояния на заблокированной строке, изменение и фиксация. Новый резерв разрешён только для чужой свободной вещи с непустым отдельным контактом. Правка разрешена только автору свободной вещи. Отмена проверяет одновременно текущий ID резерва и текущего получателя; старый ID даёт отказ без воздействия на новый резерв. Снятие автором меняет состояние на «снято» и очищает текущие поля резерва одним изменением. Отмена не возвращает снятое объявление в свободное состояние. Контакт во время резерва не редактируется.

Другой запрос после ожидания блокировки проверяет уже новое состояние. При сбое изменения откатываются; успех возвращается только после фиксации. Новый ID резерва получает сам получатель, автор видит его в разрешённом текущем представлении; третьим пользователям он не нужен. Прекращённый резерв не имеет отдельного пользовательского интерфейса истории с личными полями.

### Контрпример и уточнение цепочки

**Исходный правдоподобный вариант:** блокировать объявление и разрешать отмену, если текущий получатель совпадает с текущим пользователем. Это обеспечивает последовательность изменений, но не определяет, к какой договорённости относится команда.

**Контрпример:** B резервирует вещь A как R1, отменяет R1, затем снова резервирует ту же вещь как R2. Задержанная копия отмены R1 приходит после создания R2. Получатель снова B, состояние снова «зарезервировано»; блокировка и проверка владельца успешно проходят и прекращают R2, хотя пользователь отменял R1. Полностью последовательное исполнение здесь всё равно неверно.

**Уточнение:** T-07 включает повтор устаревшей команды, SR-05 требует сохранности нового резерва при обращении к старому, D-03 проверяет уникальный ID текущего резерва, а P3 ниже воспроизводит последовательность R1 → отмена → R2 → старая отмена. Достаточно нового ID для каждой договорённости; обещание идемпотентности всех операций API не вводится. Это обзор проектного варианта, не утверждение о дефекте существующего кода.

**Доверенные данные.** Установленный пользователь и заблокированная строка. Присланный ID обозначает цель команды и сверяется с ней; знание ID не даёт полномочий.

**Обоснование и альтернатива.** Одна строка и общая блокировка охватывают все переходы небольшого автомата состояний. Применимая альтернатива — оптимистическая версия строки с условным обновлением и отказом при изменившейся версии. Она уменьшает ожидание, но требует одинаковой проверки версии во всех операциях и повторного чтения после конфликта. Ни один из способов сам по себе не заменяет привязку отмены к R1/R2. Переход к оптимистическому варианту обоснован при измеренной высокой конкуренции, с сохранением предметной проверки ID резерва.

**Связи:** T-07 → [SR-03](SECURITY_REQUIREMENTS.md#sr-03-полномочия-и-принадлежность-объектов), [SR-04](SECURITY_REQUIREMENTS.md#sr-04-ограничение-раскрытия-данных), [SR-05](SECURITY_REQUIREMENTS.md#sr-05-целостность-объявления-и-резерва), [SR-09](SECURITY_REQUIREMENTS.md#sr-09-безопасная-обработка-ввода-и-отказов). Непосредственные связи T-07 в модели — SR-05/09; SR-03/04 задают полномочия и последствия перехода.

**Будущие проверки:**

| ID | Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- | --- |
| P1 | Свободная вещь A, два разных получателя | Синхронно начать два резерва, затем повторить запрос победителя | Ровно один успешный резерв; один текущий ID и получатель; повтор не заменяет резерв по SR-05. |
| P2 | Свободное либо зарезервированное объявление | Попарно выполнить резерв/снятие, отмену/снятие, правку/резерв; управлять порядком блокировок в обе стороны | Результат соответствует допустимой последовательности SR-05: снятое без резерва, правка только до резерва; контакт не меняется после него. |
| P3 | B отменил R1 и создал R2 той же вещи | Повторить отмену с R1, в том числе одновременно с другой операцией; затем отменить R2 | Старая команда отклоняется, R2 с контактом сохраняется; правильная отмена R2 освобождает вещь. Проверка владельца без ID дала бы иной результат. |
| P4 | Изменение до фиксации | Искусственно вызвать отказ сохранения; заново прочитать объект и выполнить независимый корректный запрос | Нет частичного перехода, старое состояние сохраняется; ответ не выдаёт успех или секреты. После успешного прекращения выдача соответствует D-02. |

**Ограничения.** Все пути записи обязаны использовать общий протокол; отдельное изменение полей в обход него разрушит гарантию. Долгие транзакции создают ожидание, поэтому внутри них нет внешних вызовов. Резерв не подтверждает передачу вещи; автоматическое истечение и повторная публикация отсутствуют.

<a id="d-04"></a>
## D-04. Согласованное бронирование, квота и сохранение истории

**Контекст.** Блокировка только комнаты не сохраняет суммарный предел одного аккаунта в разных комнатах. Проверка времени до ожидания блокировки может разрешить изменение уже начавшейся брони. Отдельное удаление старого интервала при переносе теряет исходную договорённость.

**Решение.** Для создания, переноса и отмены API открывает транзакцию `READ COMMITTED` и блокирует строку текущего аккаунта через `FOR UPDATE`. Для переноса/отмены после этого получает собственную бронь и актуальную исходную комнату; изменения броней этого аккаунта также используют эту блокировку. Затем блокирует строки исходной/целевой комнаты в возрастающем порядке ID, без повторной блокировки одной и той же комнаты. Проверки и запись выполняются после получения всех блокировок. Глобальный порядок — аккаунт, затем комнаты; операции справочника блокируют комнаты и не берут после них блокировки аккаунтов.

После ожидания API проверяет существование и доступность целевой комнаты, принадлежность и неотменённое состояние исходной брони. Текущее время берётся непосредственно перед решением об изменении через `clock_timestamp()`, а не `now()`, фиксирующий начало транзакции. Перенос/отмена допускаются только при времени строго раньше исходного начала; новое начало не в прошлом. Точкой принятия временного решения является финальная проверка перед записью после всех предметных ожиданий; более раннее время запроса не даёт разрешения. Начало передаётся с часовым поясом и может содержать секунды; длительность — целое число минут 5–360, конец вычисляет сервер. Время хранится в UTC, полуоткрытые интервалы сравниваются по условию `start1 < end2 && start2 < end1`. При переносе собственная запись исключается из проверки пересечений. [Время PostgreSQL](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

Подсчёт берёт все неотменённые брони аккаунта по московской дате начала, включая прошедшие и комнаты, исключённые из справочника. При переносе сама запись исключается из подсчёта новой даты. Счётчик не хранится отдельным уменьшаемым числом: отмена меняет состояние записи, поэтому повторная отмена не освобождает дополнительное место. Аккаунтная блокировка сериализует создания, переносы и отмены во всех комнатах, комнатная — конкуренцию разных аккаунтов. Проверки после ожидания выполняются отдельными чтениями, видящими зафиксированные изменения в `READ COMMITTED`.

Перенос обновляет ту же бронь с прежним ID и владельцем в одной транзакции. Отмена оставляет запись истории. Конфликт или сбой откатывает всё предметное изменение: исходный интервал и подсчёты сохраняются. Фиксация предшествует успешному ответу. При взаимной блокировке, тайм-ауте или отказе БД транзакция откатывается и возвращает контролируемый отказ; автоматического повторения предметной команды в этом варианте нет.

Удаление комнаты администратором получает блокировку её строки, проверяет после ожидания отсутствие неотменённых броней с концом позже текущего времени и ставит признак исключения из справочника. При создании/переносе этот признак проверяется под той же блокировкой: успела бронь — удаление отклоняется, успело удаление — бронь отклоняется. Сама строка комнаты и её название/корпус сохраняются, каскадного удаления броней нет. Переименование не входит в ядро. История доступна владельцу по D-02 и хранится до явного сброса учебных данных; такой сброс — служебная операция доверенного окружения вне пользовательского API, не обычное удаление комнаты.

**Доверенные данные.** Аккаунт из D-01, заблокированные строки комнат, сохранённая бронь, серверное время и дата начала в `Europe/Moscow`. Часы и счётчики клиента не используются.

Для текущего локального продукта выбираются явные блокировки: места координации объяснимы через комнату и аккаунт, а штатные конфликты не требуют цикла повторных попыток. Это не утверждение о лучшей производительности без измерений. Применимость альтернативы подтверждает [документация PostgreSQL об изоляции](https://www.postgresql.org/docs/current/transaction-iso.html); фактических сравнительных испытаний нет.

<a id="d-05"></a>
## D-05. Разделение ввода и команд, безопасные отказы и локальная граница

**Контекст.** Тексты объявлений и целей могут стать SQL, а диагностические ответы или опубликованная конфигурация — раскрыть повторно используемые секреты. Ошибка Compose может открыть локальную систему другим компьютерам.

**Решение.** Доступ к PostgreSQL выполняется через Npgsql: значения передаются типизированными параметрами, структура SQL определена сервером. Пользовательский ввод не выбирает имена таблиц/столбцов и не исполняется как команда. API до записи проверяет типы, обязательные поля, непустой контакт резерва и предметные ограничения; SQL-фрагменты в допустимых текстах остаются буквальными данными. Новые численные пределы текстов и политика сложности пароля на S04 не вводятся. [Параметры Npgsql](https://www.npgsql.org/doc/basic-usage.html#parameters).

Каждая предметная операция имеет единую границу фиксации по D-01/D-03/D-04. При отказе до фиксации она откатывается; по исключению не отправляется успешный ответ. Потеря соединения после commit может оставить клиенту неопределённость результата: восстановление через чтение, без обещания исполнения «ровно один раз». Учёт допущенных попыток входа/регистрации отделяется от предметного отката по D-06.

Общий обработчик возвращает контролируемую ошибку с категорией и идентификатором запроса, без исключения, SQL и конфигурации. Диагностика использует разрешённые поля: время, ID запроса, серверное имя операции и категория результата. Тела запросов/ответов, Authorization, пароль, хеш пароля, контактные тексты, email и полные исключения БД не записываются. Поиск проблемы не включает автоматическое логирование всего запроса.

Секрет подключения задаётся оператором через локальный файл окружения вне Git; примеры содержат только имена параметров и недействующие заполнители. При подготовке к публикации проверяются отслеживаемые файлы и предлагаемые к добавлению артефакты. Служебные права оператора не передаются пользователю API.

Compose публикует порт API с явной привязкой к `127.0.0.1`; PostgreSQL не содержит публикации порта хоста. API использует имя сервиса БД, а не `localhost`. Внутреннее прослушивание API в контейнере не тождественно публикации на внешнем интерфейсе хоста. Внешних прикладных вызовов нет; после первичной подготовки зависимостей операции автономны.

**Доверенные данные.** Серверная структура команд и конфигурация оператора. Строки клиента — данные; текст исключения не предназначен для клиента или обычного журнала.

**Обоснование и альтернатива.** Параметры отделяют значения от SQL независимо от кавычек и разделителей. Альтернатива — ORM с параметризованными запросами — применима, но необработанный SQL внутри неё требует тех же правил; название ORM не заменяет гарантию. Для выбранных явных блокировок Npgsql позволяет непосредственно выразить протокол. Секреты в отдельном файле подходят доверенному локальному окружению; при внешнем размещении потребуются иной канал конфигурации и пересмотр сетевой модели.

Откат конкурентных изменений — D-03/D-04, пароли и хранение сеанса — D-01.

| ID | Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- | --- |
| P1 | Учебные записи разных владельцев | Отправить SQL-фрагменты, кавычки и разделители в название, описание, контакт, цель; затем некорректные типы/поля/ID | Текст остаётся данными либо запрос отклоняется по контракту; чужие записи/права неизменны, частичных объектов нет, следующий корректный запрос выполняется. |
| P2 | Допустимая операция до commit | Вызвать отказ БД/сохранения, прочитать состояние и обычный журнал | Откат по соответствующему D, контролируемый ответ без SQL/стека/секретов; допущенная попытка аутентификации учитывается по D-06. |
| P3 | Вымышленные пароль, Bearer и секрет подключения | Выполнить вход, отказы и выход; проверить ответы, журналы и подготовленные к публикации файлы | Пароль/его хеш и конфигурация не выдаются; Bearer только в предназначенном ответе входа. Заполнители примеров не являются действующими секретами. |
| P4 | Фактическое окружение Compose после получения зависимостей | Проверить публикацию портов, запрос с loopback и другого компьютера; доступ API к БД; сценарии без внешних прикладных сервисов | Выполняются критерии SR-12: внешнее соединение не устанавливается, порт БД не опубликован, API работает с БД по имени сервиса. Результат фиксируется для конкретной конфигурации. |

**Статус S05.** Основа использует Npgsql только для постоянного `SELECT 1`, пароль подключения вне Git, loopback-публикацию API и БД без порта хоста. Ответ `/health` — фиксированный `200/ready` либо `503/unavailable`; общий предел ожидания проверки 3 секунды охватывает получение соединения и завершение команды. Запрос драйвера также получает отмену, но его освобождение ресурсов может закончиться позднее HTTP-ответа; исход такой задачи наблюдается без записи исключений. Журнал API содержит только время, серверную операцию, категорию результата и серверный ID запроса. Фактическая проверка этой основы описана в паспорте; P1–P4 в полном предметном объёме остаются будущими.

**Ограничения.** Документ не заменяет фактическую проверку портов или всей истории Git. Доверенный оператор имеет доступ к локальному секрету; его захват вне границы. Контракты предметного API и ограничения объёма запросов будут уточнены при реализации без отмены принятых свойств. `/health` не гарантирует нагрузочную устойчивость: локальный клиент может создать очередь проверок; пул ограничен десятью соединениями, а SR-10 относится к будущим входу и регистрации.

<a id="d-06"></a>
## D-06. Последовательный учёт попыток в точных скользящих окнах

**Контекст.** Простой счётчик без согласованной проверки допускает превышение при конкуренции, а фиксированные или сегментированные окна могут отличаться от точного скользящего правила. Учёт отклонённых по лимиту запросов способен продлевать отказ бесконечно.

**Решение.** API использует IP сетевого соединения, без доверия к `X-Forwarded-For` и подобным клиентским заголовкам; прокси в текущей топологии отсутствует. Адреса нормализуются единообразно, включая IPv4-mapped IPv6. Наблюдаемый контейнером адрес может быть общим для клиентов: лимит не идентифицирует человека.

В PostgreSQL хранятся события допущенных попыток с серверным временем завершения, видом операции, нормализованным email для входа и результатом проверки пароля. Для IP существует уникальная служебная строка координации. Она создаётся безопасной вставкой при отсутствии и блокируется `FOR UPDATE` до подсчёта. Общая блокировка IP используется входом и регистрацией; ожидание предшествует получению актуального времени. Проверяются события в `(t − окно, t]`: на точной нижней границе событие перестаёт учитываться.

При 10 неуспешных входах пары IP/email за 15 минут либо 100 допущенных входах IP за 15 минут новый вход отклоняется до проверки пароля. При 10 допущенных регистрациях IP за час отклоняется следующая регистрация. Такой отказ не создаёт событие и не продлевает окно. Если предел не достигнут, пароль и предметные условия проверяются, результат записывается до освобождения блокировки. Иначе два параллельных неверных пароля при девяти ошибках могли бы оба пройти предварительный подсчёт. Отсчёт события от завершения задаёт полный интервал ограничения после проверенной попытки; время ожидания не подменяет время события.

Для допущенной регистрации/входа предметная часть выполняется внутри точки сохранения той же транзакции. Ожидаемый отказ, например занятый логин или неверный пароль, откатывает только предметную часть, после чего событие фиксируется. Недопустимый формат учитывается в общем лимите операции; при отсутствии корректного email парный счётчик не применяется. При техническом отказе всей транзакции аккаунт/сеанс не создаётся и успех не выдаётся; отсутствие зафиксированного события при таком отказе не даёт обхода с получением аккаунта/сеанса. Запись событий и успех предметной части фиксируются совместно. Ответ следует после commit; после рестарта API события в БД сохраняются.

События, вышедшие из своих окон, можно удалить служебной очисткой; они не являются пользовательской историей броней. Числа 10/100/10 сохраняются как учебный компромисс S02: сдержать массовые попытки, оставив обычный ручной вход и регистрацию. Они не получены измерением нагрузки и не обещают устойчивость к любому отказу в обслуживании. Пересмотр после измерений потребует синхронизации SR-10 и паспорта.

**Доверенные данные.** Наблюдаемый IP соединения, единая нормализация email из D-01, серверные часы и сохранённые события. Клиентские часы и заявленный IP не используются.

**Обоснование и альтернатива.** Точные события соответствуют заданным скользящим окнам, общая блокировка сериализует решение и известный результат. Альтернатива — точные очереди событий в памяти одного процесса под блокировкой — проще, но теряет историю при рестарте и не объединяет несколько процессов. Постоянное хранение подходит уже выбранному PostgreSQL. Цена — последовательная обработка общего IP и транзакция на время хеширования; измеренный неприемлемый отклик или прокси потребуют пересмотра.

**Связи:** T-13 → [SR-10](SECURITY_REQUIREMENTS.md#sr-10-ограничение-массовых-попыток); нормализация, аккаунт и сеанс — D-01, контролируемые отказы — D-05.

**Будущие проверки:**

| ID | Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- | --- |
| P1 | Девять неверных входов пары IP/email | Одновременно отправить ещё два неверных пароля; затем правильный с вариантом регистра/пробелов email | Только один проходит проверку пароля как десятая ошибка; следующий и правильный до освобождения окна временно отклоняются по SR-10. |

**Ограничения.** Общий IP позволяет одному локальному клиенту временно ограничить других; постоянного наказания аккаунта нет. Счётчики не защищают от многих разных сетевых источников, захвата ОС или ошибочного времени. Внешние вызовы внутри транзакции запрещены.
