# Требования безопасности WiseDubs

## Граница и статус

WiseDubs — сервис обмена вещами и бронирования общих комнат общежития. Требования относятся к серверному API, учётным записям, объявлениям и резервам, справочнику комнат и бронированиям. Назначение, роли и сценарии описаны в [паспорте проекта](PROJECT.md).

Это рабочий набор S02: обязательные защитные свойства и критерии будущей приёмки. Выполнение требований, запуск и результаты испытаний здесь не подтверждаются. Связи с угрозами и решениями пока обозначены `—`; механизмы будут выбраны на следующих этапах. Идентификаторы сохраняются при уточнении того же свойства.

Целевой API доступен из Интернета по HTTPS, PostgreSQL недоступен пользователям напрямую. Хостинг, почтовый провайдер и инфраструктурные средства не выбраны. Локальный запуск на вымышленных данных обязателен для учебной проверки; его граница описана в SR-11.

Регистрация открыта любому человеку с email. Подтверждение почты доказывает доступ к адресу, но не личность человека или проживание в общежитии. До подтверждения доступны только регистрация, подтверждение и повторная отправка кода, а также попытка входа без выдачи действующего сеанса. Все предметные данные закрыты. Далее «пользователь» означает вошедшего пользователя с подтверждённой почтой, если не указано иное.

При отказе в изменении предметных данных защищаемые записи и связи остаются прежними. Учёт неуспешных попыток и служебная регистрация отказа допустимы. Критерии применяются к прямым запросам API, а не только к действиям интерфейса. Конкретные маршруты, формат ошибок и коды HTTP ещё предстоит определить.

## Принятые правила и предварительные допущения

Согласованы: шестизначный одноразовый код на 10 минут и максимум 5 попыток; новый код отменяет старый; повторная отправка не чаще раза в 60 секунд и максимум 5 за час на аккаунт. Сеанс действует 7 дней с момента входа без автоматического продления; выход прекращает текущий сеанс. При недоступности почты подтверждение не обходится, вход подтверждённых пользователей сохраняется.

Следующие параметры приняты **предварительно для S02**, а не представлены как ранее согласованные или измеренные:

| Операция | Рабочий предел |
| --- | --- |
| Вход для пары «IP + email» | После 10 неуспешных попыток за 15 минут новые попытки временно отклоняются |
| Вход с одного IP | Максимум 100 попыток за 15 минут, независимо от email и результата |
| Регистрация с одного IP | Максимум 10 запросов за час |
| Отправка кодов с одного IP | Максимум 20 писем за час, включая первое письмо и повторные |
| Проверка кода | После 5 неверных попыток код недействителен; новый получают с соблюдением лимитов отправки |

Для однозначной будущей проверки временные пределы трактуются как скользящие окна: попытки старше 15 минут или часа перестают учитываться. Ограничение действует, пока превышен хотя бы один применимый предел; отклонённые из-за лимита запросы не продлевают паузу. Минимальные 60 секунд отсчитываются от предыдущей отправки. Это уточнение рабочего допущения, а не выбор технического механизма. Постоянная блокировка аккаунта не вводится.

Квот числа броней нет: защита от занятия расписания множеством допустимых броней не заявляется. Сроки физического хранения и удаления архивных записей пока не установлены. Ограничение выдачи через API не означает уничтожения данных или отзыва ранее полученных пользователем сведений. Восстановление пароля, корпоративная почта и университетские интеграции находятся вне ядра.

## SR-01. Допуск после подтверждения аккаунта

**Защитное свойство.** Предметные данные и действия доступны только после проверки пароля и подтверждения email. Код подтверждает исключительно тот аккаунт, для которого выпущен, однократно и в пределах срока и числа попыток.

**Последствия нарушения.** Посторонний получает контакты и расписание, создаёт объекты от имени другого аккаунта либо использует адрес, которым не владеет.

**Критерии приёмки:**

1. Гость и неподтверждённый аккаунт не получают объявления, контакты, комнаты, расписание и историю, включая обращения по ID; создание и изменение предметных объектов отклоняются.
2. Неверный пароль, неизвестный аккаунт и правильный пароль неподтверждённого аккаунта не дают действующего сеанса. После корректного подтверждения и входа пользователь получает доступ в пределах своих прав.
3. Правильный шестизначный код до истечения 10 минут подтверждает соответствующий аккаунт. В момент истечения срока и позднее код отклоняется. Неверный, уже использованный, заменённый новым или выданный другому аккаунту код не подтверждает адрес. Два одновременных предъявления одного кода не дают двух успешных подтверждений.
4. После пяти неверных попыток даже правильное значение прежнего кода отклоняется; допустимая отправка нового кода позволяет начать подтверждение заново. Пределы запросов уточняет SR-10.
5. При сбое отправки письма аккаунт остаётся неподтверждённым, API не возвращает код как запасной способ входа. Подтверждённый пользователь с правильным паролем продолжает входить без обращения к почтовому сервису.

## SR-02. Ограниченный жизненный цикл сеанса

**Защитное свойство.** Сервер принимает только действующее подтверждение сеанса, выданного при входе этому пользователю. Сеанс прекращается через 7 дней с момента входа либо при выходе из него; обращения к API не продлевают срок.

**Последствия нарушения.** Подмена или повторное использование прекращённого сеанса позволяет читать данные и действовать от имени владельца после завершения доступа.

**Критерии приёмки:**

1. Без подтверждения сеанса, с произвольным или изменённым значением запрос к защищённому чтению или изменению отклоняется без выдачи данных и без изменения предметного состояния. Действующий сеанс допускает разрешённое действие.
2. Непрекращённый сеанс непосредственно до границы 7 дней действует; на границе и после неё отклоняется. Частые запросы в течение этих дней не сдвигают окончание срока.
3. После успешного выхода повторное использование сохранённого подтверждения текущего сеанса не позволяет читать данные или изменять объекты. Новая аутентификация выдаёт отдельный действующий сеанс; старое подтверждение остаётся непригодным.
4. Выход из одного из двух сеансов аккаунта прекращает именно этот сеанс. Другой продолжает действовать до своего выхода или срока окончания.

## SR-03. Полномочия и принадлежность объектов

**Защитное свойство.** Сервер проверяет право на конкретный объект при каждом действии. Автор изменяет своё свободное объявление и снимает своё предложение; получатель отменяет свой резерв; владелец переносит и отменяет свою бронь до начала. Администратор управляет справочником комнат, а предметными объектами — только как обычный пользователь от своего имени. Роль выдаёт и отзывает оператор вне пользовательского API.

**Последствия нарушения.** Подмена ID, автора, владельца или роли позволяет менять чужие договорённости, освобождать чужие интервалы и повреждать справочник.

**Критерии приёмки:**

1. Пользователь B подставляет ID объектов A в изменение или снятие объявления, отмену резерва, перенос или отмену брони: получает отказ, объекты A остаются прежними. Те же допустимые операции владельцев A выполняются с учётом состояния объектов.
2. Передача чужого автора, владельца или получателя при создании и изменении не позволяет действовать от чужого имени: запрос либо отклоняется, либо объект принадлежит текущему пользователю. Никакие поля запроса не меняют принадлежность существующих объектов.
3. Обычный пользователь не добавляет и не удаляет комнаты, даже обращаясь непосредственно к административной операции. Администратор добавляет комнату и удаляет её только при условиях SR-07, но не меняет чужие объявления, резервы и брони.
4. Передача административной роли при регистрации или в пользовательском запросе не выдаёт прав. После отзыва роли оператором следующие запросы прежнего администратора к справочнику на изменение отклоняются, в том числе с ранее выданным сеансом.
5. Владелец переносит или отменяет ещё не начавшуюся бронь; на границе начала и позднее обе операции отклоняются без изменения брони. Обычные действия администратора над собственными объектами подчиняются тем же ограничениям.

**Внешний ориентир.** [OWASP ASVS v5.0.0-8.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md#v82-general-authorization-design) требует явного разрешения на доступ к конкретным данным. Для WiseDubs это уточняет проверку принадлежности при прямом обращении к чужому объявлению, резерву или брони: знание ID не даёт права изменять объект. Правила разрешённого чтения определяет SR-04. Использован отдельный пункт справочника; соответствие всему ASVS и согласование с преподавателем не заявляются.

## SR-04. Ограничение раскрытия данных

**Защитное свойство.** API выдаёт только данные, разрешённые текущему пользователю и состоянию объекта. Правила одинаковы для списков, карточек, запросов по ID, вложенных объектов и ответов на изменение.

**Последствия нарушения.** Раскрываются контакт бывшего получателя, личные планы владельца брони или снятое предложение; email входа становится доступен без решения владельца его опубликовать.

**Критерии приёмки:**

1. Вошедшие пользователи с подтверждённой почтой видят контакт автора и место передачи опубликованного объявления до резерва и во время него. Гость и неподтверждённый аккаунт их не получают. Email входа автоматически не добавляется в объявление; контакт задаётся автором отдельно.
2. При резервировании обязателен отдельный контакт получателя. Пока резерв действует, автор получает имя, ID и этот контакт текущего получателя, а сам получатель — сведения о своём резерве. Третий пользователь, включая администратора, не получает этих полей через объявление, списки, резерв или вложенный профиль; ему доступен только факт занятости вещи.
3. После отмены резерва либо снятия объявления автор больше не получает через API имя, ID и контакт бывшего получателя, включая историю и ранее известный ID резерва. При новом резерве доступны только сведения текущего получателя. Ранее сохранённые за пределами API сведения этим правилом не уничтожаются.
4. Снятое объявление видно только автору в его объектах и по ID. Другие пользователи, включая бывшего получателя и администратора, не получают его содержимое ни в списках, ни по известному ID.
5. Общее расписание выдаёт комнату и занятый интервал без владельца, его контактов и цели брони. Подстановка ID чужой брони не раскрывает эти сведения. Правило действует и для администратора помещений.
6. Владелец видит собственные будущие, текущие, прошедшие и отменённые брони с целью и сведениями о комнате, в том числе после удаления комнаты из справочника. Чужая история ему недоступна; отменённая бронь не показывается как занятый интервал.

## SR-05. Целостность объявления и резерва

**Защитное свойство.** У опубликованного объявления может быть только один текущий получатель, отличный от автора. Резерв, его прекращение и снятие объявления сохраняют согласованное состояние предложения и контакта получателя.

**Последствия нарушения.** Одна вещь обещана нескольким людям, условия обмена меняются после договорённости или снятая вещь продолжает считаться доступной.

**Критерии приёмки:**

1. Два пользователя одновременно резервируют свободное объявление: ровно один получает успех и становится текущим получателем; второй получает отказ, чужой резерв не заменяется. Повторный запрос победителя не создаёт новый резерв.
2. Собственный резерв, резерв занятой или снятой вещи и резерв без отдельного непустого контакта отклоняются. Корректный резерв чужой свободной вещи связывает её с текущим пользователем и переданным контактом.
3. Попытка автора изменить название, описание, контакт автора или место передачи зарезервированной вещи отклоняется. Контакт получателя в течение резерва также не изменяется; подмена полей резерва не меняет получателя.
4. Получатель отменяет свой резерв: объявление становится свободным без текущего получателя; новая допустимая попытка резерва успешна. Автор снимает свободное или зарезервированное объявление: состояние становится «снято», активный резерв отсутствует, последующий резерв отклоняется.
5. При одновременных снятии и резервировании итог — снятое объявление без активного резерва. При одновременных снятии и отмене предложение не возвращается в свободное состояние. При конкурирующих редактировании и резервировании допустима только последовательность, в которой изменение совершено до резерва; после установления резерва условия не меняются.
6. После прекращения резерва выдача данных соответствует SR-04. Ни один успешный ответ не должен оставлять снятое объявление с действующим резервом.

## SR-06. Достоверность занятости комнат

**Защитное свойство.** Для одной комнаты нельзя подтвердить пересекающиеся действующие брони; создание и перенос сохраняют корректные интервалы, а отказ в переносе не лишает владельца исходного времени.

**Последствия нарушения.** Пользователи получают несовместимые обещания доступа, теряют уже занятую комнату либо занимают время запросом с недопустимыми параметрами.

**Критерии приёмки:**

1. Допустимый свободный интервал существующей комнаты создаёт одну бронь за текущим пользователем. Начало не в прошлом, длительность — от 5 минут до 6 часов включительно в целых минутах, время содержит часовой пояс. Запросы с прошлым началом, отсутствующим поясом, дробной длительностью, длительностью менее 5 или более 360 минут, нулевым или обратным интервалом отклоняются без изменения расписания. Те же ограничения действуют при переносе.
2. При существующей брони 10:00–11:00 запросы 10:30–11:30, 09:30–10:30, 10:15–10:45, 09:00–12:00 и 10:00–11:00 той же комнаты отклоняются. Интервалы 09:00–10:00 и 11:00–12:00 допускаются при отсутствии других конфликтов. Примеры относятся к будущей дате и одному часовому поясу.
3. Два одновременных создания на пересекающиеся интервалы свободной комнаты дают ровно одну подтверждённую бронь. Аналогично конкурирующие создание и перенос либо два переноса не оставляют пересечений. Одновременные соседние интервалы допускаются; одинаковое время разных комнат само по себе конфликтом не является.
4. Успешный перенос освобождает старый интервал и занимает новый. Пересечение с прежним интервалом самой переносимой брони не даёт ложного отказа. При конфликте нового интервала, недопустимых параметрах или отказе сохранения исходная бронь, её владелец и интервал остаются прежними; новый интервал не занимается частично.
5. Отмена владельцем до начала освобождает время: другой пользователь может его забронировать, а отменённая запись остаётся в истории владельца. Принадлежность и запрет изменений с момента начала проверяются по SR-03.
6. Два представления одного момента с разными часовыми поясами дают одинаковый результат проверки пересечения. Хранение в UTC и представление в Europe/Moscow не позволяют обойти занятость.

## SR-07. Сохранность справочника и истории

**Защитное свойство.** Удаление комнаты не нарушает текущие и будущие брони и сохраняет сведения о прошедших и отменённых бронированиях. Новая бронь удалённой комнаты невозможна.

**Последствия нарушения.** Подтверждённая встреча остаётся без помещения, история исчезает либо пользователь получает бронь объекта, которого уже нет в справочнике.

**Критерии приёмки:**

1. Удаление администратором комнаты с неотменённой текущей или будущей бронью отклоняется; запись комнаты и брони сохраняются. Отменённые и завершившиеся брони не препятствуют удалению.
2. Комната без текущих и будущих броней удаляется из доступного справочника; новые брони по её старому ID отклоняются. Владельцы по-прежнему видят историю с комнатой, интервалами, целью при наличии и состоянием своих прошедших и отменённых броней.
3. При одновременных удалении комнаты и создании либо переносе брони в неё результат соответствует одной допустимой последовательности: бронь успела закрепиться — удаление отклоняется; удаление произошло первым — бронирование отклоняется. Во втором случае неуспешный перенос сохраняет исходную бронь. Брони удалённой комнаты не возникает.
4. Удаление комнаты не даёт администратору доступ к владельцам и целям чужих броней. История сохраняет ограничения SR-04.

## SR-08. Защита учётных данных и секретов

**Защитное свойство.** Пароли сохраняются только как данные для проверки по хешу, без открытого или обратимо зашифрованного пароля. Пароли, коды, действующие подтверждения сеанса и секреты конфигурации не раскрываются в обычных ответах API, журналах и публичных материалах.

**Последствия нарушения.** Чтение хранилища, журнала или документации позволяет захватить аккаунт, подтвердить чужой адрес либо получить доступ к инфраструктуре.

**Критерии приёмки:**

1. После регистрации и входа вымышленного пользователя инспекция сохранённых данных не обнаруживает исходный пароль или его обратимо зашифрованную копию. Правильный пароль проходит проверку, неправильный — нет. Алгоритм и параметры хеширования предстоит выбрать.
2. При регистрации, подтверждении, входе, отказах, выходе и предметных операциях ответы и обычные журналы не содержат пароль, код, хеш пароля, секреты конфигурации или действующее подтверждение сеанса. Предусмотренные исключения: код в письме его адресату и подтверждение сеанса в предназначенном для этого ответе успешного входа тому же пользователю; они не дублируются в журналах.
3. При истечении кода, превышении лимита и сбое почтовой доставки ответ не раскрывает ожидаемый код. Письмо с кодом не включает пароль, подтверждение сеанса или инфраструктурные секреты.
4. Публикуемые файлы, примеры конфигурации и демонстрационные материалы не содержат действующих секретов и реальных учётных данных. Будущая проверка охватывает подготовленные к публикации артефакты; сам этот критерий не подтверждает проверку всей истории репозитория.

## SR-09. Безопасная обработка ввода и отказов

**Защитное свойство.** Недопустимый ввод и отказ обработки не приводят к неразрешённому или частичному изменению состояния. Пользовательские строки обрабатываются как данные, а ошибки не раскрывают внутренние исключения, запросы к БД и секреты.

**Последствия нарушения.** Ввод превращается в команды, повреждает предметные записи или раскрывает сведения для дальнейшего доступа к данным и инфраструктуре.

**Критерии приёмки:**

1. Некорректный формат запроса, отсутствующие обязательные поля, неверные типы и несуществующие ID дают контролируемый отказ без создания частичного объявления, резерва или брони. После отказа следующий корректный независимый запрос выполняется.
2. Строки с SQL-фрагментами и разделителями команд в названии, описании, контакте и цели брони либо отклоняются по контракту, либо сохраняются как буквальные данные. Они не меняют чужие записи, не меняют права и не вызывают выполнение команд вне предметной операции.
3. Искусственно вызванный при будущей проверке отказ БД или обработки запроса не возвращает клиенту стек вызовов, текст SQL, строки подключения и секреты. Клиент получает понятный отказ, а повторное чтение не обнаруживает частично выполненную операцию.
4. При отказах конкурентных операций сохраняются инварианты SR-05–SR-07. Служебные журналы подчиняются SR-08; диагностический текст не заменяет успешный результат операции.

## SR-10. Ограничение массовых попыток

**Защитное свойство.** Вход, регистрация, отправка и проверка кодов ограничиваются по указанным выше пределам, включая конкурентные запросы. Ограничения сдерживают подбор пароля и кода и массовую отправку писем, сохраняя возможность продолжить допустимую работу после паузы.

**Последствия нарушения.** Автоматизированные попытки упрощают захват аккаунта, расходуют ресурсы регистрации и почты либо превращают временный предел в бессрочный отказ владельцу.

**Критерии приёмки:**

1. После 10 неверных входов за 15 минут с одного IP для одного email следующая попытка этой пары отклоняется временно, даже с правильным паролем. Другой email с того же IP учитывается отдельно по паре, но общий 101-й вход за 15 минут с этого IP отклоняется независимо от email и результата предыдущих попыток.
2. Первые 10 запросов регистрации за час с одного IP допускаются к обычной проверке; 11-й отклоняется без создания аккаунта и отправки письма. Это не обещает успех запросам с недопустимыми данными.
3. Повторная отправка ранее 60 секунд после предыдущей не создаёт нового письма или кода; по истечении 60 секунд возможна, если остальные пределы не исчерпаны. После 5 повторных писем за час на аккаунт следующее отклоняется; 21-е письмо за час с одного IP отклоняется с учётом первого и повторных писем. Смена IP не обходит предел аккаунта.
4. Принятая отправка нового кода отменяет прежний. Пять неверных проверок делают текущий код недействительным; дальнейшее предъявление правильного старого кода не подтверждает аккаунт. Новый код выдаётся только при соблюдении всех пределов отправки.
5. Одновременные запросы у границы лимита не увеличивают допустимое число входов, регистраций, писем или попыток кода. Отказ из-за лимита не создаёт сеанс, предметный объект, письмо или новый код и не меняет пароль, роль либо статус подтверждения аккаунта.
6. Когда старые события выходят из соответствующего окна и выдержаны 60 секунд для отправки, допустимые операции снова проходят обычную проверку. Отклонённые из-за лимита запросы не продлевают паузу. При отсутствии новой активности восстановление занимает не более 15 минут для входа и часа для регистрации/отправки. Исчерпанный код при этом не оживает — требуется новый.

## SR-11. Защита сетевой передачи

**Защитное свойство.** При целевом размещении в Интернете учётные данные, подтверждения сеанса, коды и защищённые данные передаются между клиентом и API по HTTPS с проверкой подлинности сервера. Незашифрованный HTTP не обслуживает эти операции; PostgreSQL недоступен пользователям напрямую.

**Последствия нарушения.** Посредник в сети читает или подменяет пароль, сеанс, контакты и параметры операций либо обращается к данным в обход API.

**Критерии приёмки:**

1. При обращении штатного клиента к целевому HTTPS-адресу проверка сертификата и имени сервера проходит без отключения проверки; допустимая защищённая операция выполняется. При недоверенном или несоответствующем имени сертификате клиент не передаёт секреты.
2. Обращение по HTTP к регистрации, входу, подтверждению и предметным операциям не обрабатывает учётные данные, не создаёт сеанс и не выдаёт защищённые данные. HTTP либо недоступен, либо возвращает только отказ/перенаправление на HTTPS без таких данных. Клиент начинает отправку секретов сразу по HTTPS: перенаправление не защищает уже отправленный по HTTP пароль.
3. Из пользовательской внешней сети нельзя установить прямое соединение с PostgreSQL; чтение и изменение предметных данных идут через API с его проверками.
4. Для локальной учебной проверки допускается HTTP на loopback с вымышленными данными и без публикации сервера во внешнюю сеть. Такой запуск позволяет проверять предметные SR, но не подтверждает защиту интернет-размещения. Для SR-11 отдельно потребуется окружение с HTTPS; точная инфраструктура пока не выбрана.
